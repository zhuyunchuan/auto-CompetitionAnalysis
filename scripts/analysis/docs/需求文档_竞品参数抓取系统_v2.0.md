## 2. 背景与目标

### 2.1 背景

当前需要持续跟踪 Hikvision（海康威视）与 Dahua（大华）两大品牌的网络摄像机产品参数，并沉淀为结构化数据，支持后续人工分析与策略研判。在完成基础数据采集后，需要进一步对两家品牌的产品进行跨品牌对标与参数差异分析，以支撑产品规划与竞争策略决策。

### 2.2 目标

1. **数据采集**：周期性抓取两家官网目标产品的完整层级与参数信息。
2. **结构化输出**：将抓取结果标准化并输出为可直接使用的 Excel 和 CSV 宽表。
3. **跨品牌对标**：自动匹配 Hikvision 与 Dahua 的同类产品型号，建立对标关系。
4. **参数差异分析**：对对标型号进行关键参数逐项对比，识别差异与优劣势。
5. **分析报告生成**：自动生成竞品分析报告，涵盖对标总览、参数差异明细和系列覆盖度。
6. **人工可介入**：支持人工补录、复核与修订，形成可持续迭代的数据资产。

### 2.3 核心原则

1. **先爬虫、再分析**：系统分为数据采集（Phase 1）和竞品分析（Phase 2）两个独立阶段，采集先行、分析后续。
2. **爬虫与分析解耦**：采集层（Node.js Playwright）与分析层（Python Pipeline）相互独立，各自可独立迭代和部署。
3. **两阶段可独立运行**：Phase 1 可独立产出数据资产（CSV/JSONL），Phase 2 可基于已有数据随时运行分析。
4. **层级优先**：每个产品必须绑定 `brand → series_l1 → series_l2 → model` 完整路径。
5. **页面即真相**：系列/子系列以官网页面当期可见结构为准，不依赖静态字典。
6. **人工可介入**：人工补录和修订优先级高于机器抽取。

### 3.2 In Scope

1. Hikvision Pro / Value / HiLook 系列的层级发现与规格抓取。

1. 大模型辅助策略分析（后续 Phase 4 接入）。

## 5. 技术架构

### 5.1 整体架构

系统采用**双层解耦架构**，数据采集层（Node.js Playwright）与竞品分析层（Python 分析模块）相互独立，通过 CSV/JSONL 数据文件进行衔接。

```
+---------------------------------------------------------------+
|              Phase 1: 数据采集层 (Node.js Playwright)          |
|                                                                |
|  结构发现脚本 → 批量抓取脚本 → 宽表转换脚本                    |
|  统一入口: run.mjs / run.bat                                   |
|                                                                |
|  +------------------+  +------------------+                    |
|  | Hikvision Adapter|  |  Dahua Adapter   |                    |
|  | (Pro/Value/HiLook)|  | (WizSense 2/3)  |                    |
|  +------------------+  +------------------+                    |
+---------------------------------------------------------------+
                    |
                    | CSV 长表 / 宽表 / JSONL 数据交付
                    v
+---------------------------------------------------------------+
|          Phase 2: 竞品分析层 (scripts/analysis/)               |
|                                                                |
|  型号对标匹配 → 参数差异分析 → Excel 报告生成                 |
|  统一入口: run_analysis.py                                     |
|                                                                |
|  +------------------+ +------------------+ +-----------------+ |
|  | model_matcher.py | |param_comparator.py| |analysis_report| |
|  | (型号对标匹配)   | |(参数差异分析)     | |(报告生成)      | |
|  +------------------+ +------------------+ +-----------------+ |
+---------------------------------------------------------------+
```

## 7. Phase 2: 竞品分析需求

### 7.1 跨品牌型号对标匹配

#### 7.1.1 目标

自动匹配 Hikvision 与 Dahua 的同类产品型号，建立跨品牌对标关系，为参数差异分析提供基础。

#### 7.1.2 对标维度

| 维度 | 字段编码 | 权重 | 说明 |
|------|---------|:----:|------|
| 分辨率 | resolution | 0.25 | 2MP/4MP/5MP/8MP/12MP |
| 镜头类型 | lens_type | 0.15 | 固定/变焦/鱼眼 |
| 焦距 | focal_length | 0.10 | 焦距范围对比 |
| 补光方式 | supplement_light | 0.12 | ColorVu/IR/双光/无补光 |
| 补光距离 | light_range | 0.08 | 补光有效距离 |
| 防护等级 | protection | 0.08 | IP67/IP66/IK10等 |
| 光圈 | aperture | 0.07 | f/1.0 ~ f/2.8 |
| AI 功能 | ai_function | 0.10 | 智能功能对比 |
| 压缩标准 | compression | 0.05 | H.264/H.265等 |

#### 7.1.3 匹配策略

1. **参数解析**：从宽表中解析关键参数，提取数值、分类或集合类型值。
2. **相似度评分**：对每个对标维度计算归一化相似度分数（0-1），按权重加权求和得到综合匹配分数。
3. **阈值过滤**：综合匹配分数 ≥ 0.5（默认值，可配置）的型号对保留为候选对标关系。
4. **Top-K 过滤**：每个型号保留匹配分数最高的 K 个对标（默认 K=5），避免过多匹配。
5. **人工校正**：预留字段 `is_manual_confirmed` 支持人工确认/拒绝。

#### 7.1.4 输出

对标关系表（`model_mapping`）：

| 字段 | 类型 | 说明 |
|------|------|------|
| mapping_id | string | 对标关系唯一标识 |
| hikvision_model | string | Hikvision 型号 |
| hikvision_series_l1 | string | Hikvision 一级系列 |
| hikvision_subseries | string | Hikvision 子系列 |
| dahua_model | string | Dahua 型号 |
| dahua_series_l1 | string | Dahua 一级系列 |
| dahua_subseries | string | Dahua 子系列 |
| confidence_score | float | 匹配置信度（0-1） |
| match_dimensions | string | 匹配的维度列表 |
| is_manual_confirmed | boolean | 是否经人工确认 |
| created_at | datetime | 创建时间 |

### 7.2 参数差异分析

#### 7.2.1 目标

对已建立对标关系的型号对，进行关键参数逐项对比，识别参数差异、缺失和优劣势。

#### 7.2.2 分析维度

共支持 18 组可对比字段，根据宽表实际情况动态配对：

| 字段编码 | 对比策略 | 严重级别 | 说明 |
|---------|---------|:----:|------|
| resolution | numeric | P1 | 分辨率数值对比 |
| lens_type | exact | P1 | 镜头类型（固定/变焦/鱼眼） |
| focal_length | exact | P1 | 焦距范围 |
| aperture | numeric | P2 | 光圈数值大小 |
| supplement_light | set | P2 | 补光方式 |
| light_range | numeric | P2 | 补光距离（米） |
| protection | set | P2 | 防护等级 |
| compression | set | P3 | 视频压缩标准 |
| main_stream | exact | P3 | 主码流参数 |
| min_illumination | exact | P3 | 最低照度 |
| sensor | exact | P3 | 图像传感器 |
| interface | set | P3 | 接口差异 |
| ai_function | set | P2 | AI 功能 |
| power | exact | P3 | 电源供给 |
| power_consumption | numeric | P3 | 功耗 |
| operating_conditions | exact | P3 | 工作条件 |
| dimensions | exact | P3 | 尺寸 |
| weight | numeric | P3 | 重量 |

#### 7.2.3 差异类型

| 差异类型 | 标识 | 说明 |
|---------|------|------|
| 双方一致 | `match` | 参数值完全相同 |
| 数值差异 | `value_diff` | 数值型参数存在差异 |
| 功能差异 | `feature_diff` | 集合型参数存在差异（标注独有项） |
| 单方缺失 | `one_side_missing` | 一方有值，另一方无值 |
| 双方缺失 | `both_missing` | 双方均无此参数 |

#### 7.2.4 严重级别

| 级别 | 色标 | 说明 |
|------|------|------|
| P1 | 红色 | 核心功能差异，影响选型 |
| P2 | 橙色 | 重要参数差异，需关注 |
| P3 | 黄色 | 一般参数差异，辅助参考 |
| - | 绿色/灰色 | 一致或缺失，无差异 |

#### 7.2.5 输出

参数差异记录（`param_diff`）：

| 字段 | 类型 | 说明 |
|------|------|------|
| mapping_id | string | 关联的对标关系 ID |
| field_code | string | 参数字段编码 |
| field_name | string | 参数字段名称 |
| hikvision_value | string | Hikvision 参数值 |
| dahua_value | string | Dahua 参数值 |

## 9. 发现的技术问题与修复记录

### 9.1 Hikvision Pro 系列 AEM API 组件名不统一

**问题**：Pro 系列的 AEM 组件注册名为 `search_list_copy`，不是常规的 `search_list`。旧脚本假设所有系列 API 路径相同，直接拼接 `search_list.json`，导致 404 错误。

**修复**：改为从页面 HTML 中动态正则匹配 `/content/hikvision/.../responsivegrid/(search_list[^"']*)`，自动检测实际组件名。

**影响**：Pro 系列从 9 个子系列（含 1 个放错位置的）正确抓取到 8 个子系列，所有型号正确分组。

### 9.2 Dahua WizSense 2 硬编码 tab 过滤

**问题**：WizSense 2 的 `buildSeries()` 函数对 tab 做了硬编码过滤：

```javascript
tabs.filter((t) => {
  const l = t.toLowerCase();
  return l.includes("wizcolor") || l === "ir" || l.includes("smart dual light");
})
```

导致 "4G Camera" tab 被遗漏，只有 "WizColor"、"Smart Dual Light"、"IR" 被抓取。

**修复**：删除过滤逻辑，改为 `const selectedTabs = tabs;` 保留所有发现的 tab。

**影响**：WizSense 2 从 **3 个子系列** 扩展到 **4 个子系列**（新增 4G Camera，2 个型号）。

### 9.3 Playwright Chromium 缺失

**问题**：沙箱环境中未预装 Playwright 浏览器二进制文件，首次运行时报错 `Executable doesn't exist`。

**修复**：运行 `npx playwright install chromium` 下载 Chromium + FFmpeg，发现 headless shell 下载超时后，手动指定 `executablePath` 指向完整 Chrome 浏览器。

**影响**：所有 Playwright 脚本可正常运行。

### 9.4 输出路径硬编码为 Linux

**问题**：所有脚本的 `outDir` 硬编码为 `/workspace/results/...`（Linux 路径），在 Windows 环境中无效。

**修复**：改为 `D:\\work\\auto-CompetitionAnalysis\\results\\...`。

**影响**：输出文件正确写入 Windows 文件系统。

### 9.5 Value 系列 fallback 变量名错误

**问题**：Value 系列的 API fallback 路径中写的是 `models` 而不是 `models: products`，引用未定义变量会导致运行时错误。

**修复**：修正为 `models: products`。

### 9.6 Chromium 子进程文件沙箱冲突

**问题**：Chrome 子进程尝试写入 system-level 日志（`debug.log`、`sgephook_chrome.exe.log`），被沙箱环境拦截。

**影响**：仅产生非致命沙箱警告，不影响抓取数据正确性，忽略即可。

## 12. 执行流程（端到端）

### 12.1 完整流程（5 Phase）

```
Phase 1: 层级结构发现（Node.js Playwright）
  ├── 运行 hikvision_structure_by_filter.mjs
  │   └── 输出: structure_filtered.json (Pro/Value/HiLook)
  └── 运行 dahua_wizsense_structure.mjs
      └── 输出: dahua_wizsense_structure.json (WizSense 2/3)

Phase 2: 批量规格抓取（Node.js Playwright）
  ├── 运行 hikvision_batch_specs_from_structure.mjs
  │   ├── 基于 structure_filtered.json
  │   └── 输出: specs_long.csv + jsonl
  └── 运行 dahua_batch_specs_from_structure.mjs
      ├── 基于 dahua_wizsense_structure.json
      └── 输出: specs_long.csv + jsonl

Phase 3: 宽表生成（Node.js + Python）
  ├── 运行 normalize_specs.py (Hikvision)
  │   └── 输出: specs_wide.csv (694×140)
  └── 运行 normalize_specs.py (Dahua)
      └── 输出: specs_wide.csv (191×121)

Phase 4: 跨品牌型号对标匹配（Python）
  ├── 运行 model_matcher.py
  │   ├── 输入: hikvision/dahua 宽表
  │   └── 输出: model_mapping.csv

Phase 5: 参数差异分析与报告生成（Python）
  ├── 运行 param_comparator.py
  │   ├── 输入: 宽表 + model_mapping.csv
  │   └── 输出: param_diff.csv
  └── 运行 analysis_report.py
      ├── 输入: model_mapping.csv + param_diff.csv
      └── 输出: competitor_analysis.xlsx
```
